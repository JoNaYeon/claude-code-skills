# 기획서 세트 생성 — Planning Document Suite

> 목적: 하나의 프로젝트(코드베이스 + 도메인 컨텍스트)를 입력받아, **PM부터 배포까지(01~07) 표준 기획서 세트**를 일관된 컨벤션으로 한 번에 생성한다.
> 산출 위치: `기획서/` 폴더(또는 사용자 지정 경로) 아래에 01~07 카테고리 폴더 + 각 문서 `_v1.0.md`, 마지막에 `00_검토체크리스트_v1.0.md`.

## 1. Trigger

- "기획서 만들어줘", "기획서 세트", "프로젝트 문서 세트 만들어줘"
- "PRD / SRS / 서비스기획서 / HLD 만들어줘" (개별 문서 요청 시 해당 문서만 생성)
- 새 프로젝트 또는 기존 코드베이스를 문서화(As-Is 정리)할 때

---

## 2. Input

| 입력 | 필수 | 설명 |
|------|:---:|------|
| 프로젝트 설명 | ✅ | 시스템명, 목적, 핵심 기능 (자유 형식) |
| 코드베이스 경로 | 선택 | 있으면 As-Is 사실(API/DB/아키텍처)을 코드에서 추론 |
| 대상 범위 | 선택 | 전체 세트 vs 특정 카테고리(예: 03_기획만) |
| 출력 경로 | 선택 | 기본값 `기획서/` |
| docx 변환 여부 | 선택 | 기본은 `.md`만. 요청 시 docx 별도 변환 |

> 코드베이스가 없으면 사실 항목도 "제안/가정"으로 작성하고 `💡방식제안` 또는 `[ ]`로 명시한다.

## 3. Process — 한 번에 생성 (3 Phase)

### Phase 1: 컨텍스트 수집 (작성 전)
1. 프로젝트 설명을 읽고 **시스템명·목적·역할(user/admin)·핵심 기능**을 1문단으로 요약.
2. 코드베이스가 있으면 빠르게 스캔:
   - 라우트/엔드포인트 → API 명세 근거
   - DB 스키마/모델 → DB 설계 근거
   - 디렉토리/계층 구조 → 아키텍처·HLD 근거
   - 외부 연동(LLM, 결제, 메시징 등) → 제약·위험 근거
3. **앵커 문서를 먼저 확정**: `03_기획/01_서비스기획서` 의 범위(In/Out)·핵심가치·역할. 이후 모든 하류 문서가 여기에 정합되어야 한다.

### Phase 2: 문서 일괄 생성
- **반드시 `01_PM` ~ `07_배포` 7개 폴더 전체를 생성한다.** 아래 §4 생성 매니페스트의 `★` 문서는 항상 생성, `◇` 문서는 도메인에 맞으면 생성하되 폴더 자체는 건너뛰지 않는다.
- 작성은 **상류→하류 순서**(03_기획 앵커 → 04_설계 As-Is → 03_정책 → PRD/SRS → 01_PM → 02_마일스톤 → 05/06/07 가이드)로 진행해 하류 재작업을 방지.
- 각 문서는 §5 컨벤션을 따른다.
- 도메인 특화 `◇` 문서(예: 룰엔진가이드, LLM프롬프트관리, 판정정확도검증서)가 해당 프로젝트에 없으면 **생략하되 체크리스트에 "해당없음"으로 명시**한다 (말없이 빠뜨리지 않는다).
- 완료 전 §4-1 자가점검: 7개 폴더 + 모든 `★` 문서 + `00_검토체크리스트`가 실제로 생성됐는지 파일 목록으로 확인.

### Phase 3: 검토 체크리스트 생성 (마지막)
- 전체 문서를 **상류→하류 검토 순서**로 정렬한 `00_검토체크리스트_v1.0.md` 생성 (§6 형식).
- 문서 전반에서 반복 등장하는 **핵심 결정 대기 목록**을 한 표로 모음.

## 5. 작성 컨벤션 (모든 문서 공통)

### 5-1. 헤더 / 푸터
```markdown
# <문서명> (<영문 약어>) — <시스템명>

> 작성일: YYYY-MM-DD · 버전 vN.0 · 기준: As-Is
> 상위 문서: [서비스 기획서](상대경로) · 연계: [SRS](상대경로)

---
```
- 작성일은 오늘 날짜(상대표현 금지, 절대날짜로).
- 상호 참조는 **상대경로 마크다운 링크**로 연결 (예: `[HLD](../04_설계/01_HLD_v1.0.md)`).

### 5-2. 마커 체계 (문서 본문)
| 마커 | 의미 |
|------|------|
| `🔴법무` | 법무 검토/승인 필요 |
| `🏢내규` | 사내 규정 의존 |
| `🔬임상` (또는 도메인 전문가) | 전문가 검증 필요 |
| `💡방식제안` | 우리가 제안하는 방식 (확정 아님) |
| `` `[ ]` `` | 빈칸 = 결정/위임 지점 (비즈니스 항목: 발주·예산·R&R·일정 등) |
| `✅` | 코드에서 확인된 구현 완료 항목 |

### 5-3. 작성 원칙
- **코드 도출 항목(사실)은 작성, 비즈니스 항목은 `[ ]` 빈칸**으로 비워 운영팀 확정에 위임.
- 요구사항은 **ID 부여**: 기능 `PR-XXX-N`/`FR-N`, 위험 `R-<영역>-NN`, 테스트 `TC-NN`.
- 우선순위 표기: `M`(Must)/`S`(Should)/`C`(Could).
- 표를 적극 활용, 한국어 간결체, **핵심 키워드 강조**.
- 추측을 사실처럼 쓰지 않는다 — 불확실하면 `💡방식제안` 또는 `[ ]`.

### 5-4. 버전 관리
- 소스는 `_v1.0.md`. 확정/대규모 수정 시 `_v2.0`으로 버전업.
- docx 변환은 **요청 시에만** 별도 수행 (`.md`가 정본).

## 6. 검토 체크리스트 형식 (00_검토체크리스트)

상류→하류 검토 순서로 우선순위 그룹을 나누고, 각 문서를 한 행으로:

```markdown
## N순위 — <그룹명>

| 상태 | 문서 | 유형 | 확인 포인트 | 결정/위임 |
|:---:|------|:---:|------------|----------|
| ☐ | [문서명](상대경로) | 🟦/🟨/🟥 | 핵심 확인사항 | 위임처 |
```

- 상태: `☐ 미검토` → `◐ 검토중` → `☑ 확정`
- 검토유형: **🟦사실**(코드 추론·정확성 검증) / **🟨판단**(방향 결정) / **🟥위임**(법무·전문가·일정)
- 권장 우선순위 그룹:
  1. **앵커** — 서비스기획서
  2. **As-Is 사실 검증** — HLD·API·DB·SRS (오류 시 하류 전파 → 먼저)
  3. **정책 판단** — 정책정의서·PRD
  4. **PM** — 위험·품질·형상·프로젝트정의서
  5. **개발/배포/QA 가이드** (참조성)
  6. **외부 위임 그룹** — 약관·개인정보·정확도검증·마일스톤
- 마지막에 **핵심 결정 대기 목록** 표 (여러 문서에 반복 등장하는 결정사항 통합).

## 7. Output

- 기본: `기획서/` 아래 폴더 트리 + `_v1.0.md` 파일들 + `00_검토체크리스트_v1.0.md`.
- 생성 후 요약 보고: 생성한 문서 목록, `[ ]` 빈칸으로 남긴 **위임/결정 지점 수**, 도메인상 **생략한 문서**.
- docx 필요 시 사용자에게 변환 여부를 묻고 진행.

## 8. Conventions
- 문서 언어: 한국어 (프로젝트 언어에 맞춤)
- 정본은 `.md`, docx는 파생본
- 사실/판단/위임을 항상 구분 표기 — AI가 비즈니스 결정을 임의로 채우지 않는다
- 앵커(서비스기획서) 확정 전에는 하류 문서를 "초안" 상태로 표기
